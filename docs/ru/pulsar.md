# Apache Pulsar {#apache-pulsar}

`ruststream-pulsar` запускает сервис RustStream на Apache Pulsar. Топик - это журнал, который
брокер хранит, поэтому подписка по нему перематывается. Вы можете выбрать один из четырёх типов
подписки, подписаться на список топиков или на шаблон и задать политику dead-letter на стороне
консьюмера. Фича `testing` даёт брокер внутри процесса. Про понятия самого фреймворка (подписчики,
маршрутизация, кодеки, middleware) читайте
[документацию RustStream](https://powersemmi.github.io/ruststream/).

```toml
ruststream = { version = "0.7", features = ["macros"] }
ruststream-pulsar = "0.7"
serde = { version = "1", features = ["derive"] }
```

Для сборки нужен `protoc` в `PATH`: клиент компилирует определения протокола Pulsar.

## Совместимости {#capabilities}

Какие необязательные трейты-совместимости фреймворка этот брокер реализует нативно. Совместимость,
которой у него нет, не компилируется в точке монтирования.

| Совместимость | Нативно | Почему |
| --- | --- | --- |
| `Subscribe` | да | подключённый брокер подписывается по имени топика и открывает подписку `Shared` с именем `ruststream` |
| `BatchSubscriber` | на стороне клиента | клиент отдаёт по одной доставке за раз, поэтому пакеты собираются на клиенте (см. [Пакеты](#batches)) |
| `TransactionalPublisher` | нет | клиент не реализует транзакции Pulsar |
| `OwnedTransactions` | нет | клиент не реализует транзакции Pulsar |
| `RequestReply` | нет | в Pulsar нет ящика для ответов: ответ - это обычная публикация в другой топик |
| `Partitioned` | да | доставка сообщает ключ партиционирования сообщения, по которому упорядочивают подписки `KeyShared`; при публикации ключ задают шагом `partition_key` (см. [Настройки на сообщение](#per-message-settings)) |
| `Seekable` / `Positioned` | да | подписка перематывается по `PulsarPosition`, а обработчик читает текущую позицию и ручку перемотки по ключам контекста `Position` и `SeekHandle` (см. [Перемотку](#seeking)) |
| `DescribeServer` | да | `PulsarBroker` сообщает хост и порт из своего URL и протокол `pulsar` - именно их называет документ AsyncAPI фреймворка; учётные данные из URL он не сообщает никогда |

## Жизненный цикл {#the-lifecycle}

Каждое состояние - отдельный тип, и каждый переход поглощает предыдущее:

```text
PulsarBroker::new(url)     только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedPulsarBroker    живой клиент; подписки и издатели
  .shutdown()  ->  ()                       завершающий переход
```

`new` записывает URL и не делает ввода-вывода, поэтому сервис на Pulsar собирается обычным макросом
`#[ruststream::app]`. Рантайм подключается один раз при старте, до того как откроет хоть одну
подписку.

URL задают со схемой `pulsar://` или `pulsar+ssl://`, а аутентификацию JWT вы можете добавить
вызовом `token(jwt)`. Клиент сам переподключает консьюмеров и продюсеров после перезапуска брокера.

`shutdown` поглощает подключённый брокер, поэтому публикация и подписка после него не компилируются.
Он закрывает продюсеров, которых открыл этот крейт. Своего закрытия у клиента нет, поэтому в
завершающем состоянии нет диагностики. Издатель, выданный раньше, после остановки возвращает
ошибку `PulsarError::NotConnected` вместо того чтобы переподключиться.

## Адресация топиков {#topic-addressing}

Имя топика Pulsar задаёт сразу четыре независимые величины: персистентность, арендатора,
пространство имён и сам топик. Клиент принимает имя обычной строкой, а отклонить неправильное
оставляет брокеру. `PulsarTopic` - это то же имя, проверенное при конструировании:

- `PulsarTopic::persistent(tenant, namespace, topic)` и `PulsarTopic::non_persistent(..)` собирают
  имя из частей. Они паникуют на пустой части и на части, где есть что-то кроме букв ASCII, цифр,
  `-`, `_` и `.`, поэтому годятся для литералов в коде.
- `PulsarTopic::parse(name)` возвращает ошибку вместо паники и подходит для недоверенного ввода. Он
  принимает полное имя (`persistent://acme/orders/created`), тройку `tenant/namespace/topic`
  (персистентность по умолчанию) или голое имя топика (по умолчанию `persistent://public/default/`).

Дескриптор подписки разбирает каждый названный топик до любого ввода-вывода, а публикация разбирает
свой адрес так же, когда открывает продюсера этого топика.

## Дескрипторы подписки {#subscription-descriptors}

`PulsarSubscription` - дескриптор одной подписки: он называет имя подписки, топики, которые она
читает, и настройки, с которыми открывается её консьюмер.

| Метод | Что задаёт | Умолчание |
| --- | --- | --- |
| `PulsarSubscription::new(topic, subscription)` | один топик | - |
| `PulsarSubscription::topics([..], subscription)` | фиксированный список топиков | - |
| `PulsarSubscription::pattern(regex, subscription)` | каждый подходящий топик в пространстве имён поиска | - |
| `subscription_type(SubscriptionType)` | как конкурирующие консьюмеры делят подписку | `Shared` |
| `dead_letter(DeadLetter)` | политика dead-letter на стороне консьюмера | нет |
| `ack_timeout(Duration)` | повторно доставлять сообщения, не подтверждённые дольше этого срока | нет |
| `batch_wait(Duration)` | сколько неполный пакет ждёт новых доставок (см. [Пакеты](#batches)) | 10 мс |

Четыре типа - собственные типы Pulsar:

| Вариант | Что означает |
| --- | --- |
| `Exclusive` | подписку держит один консьюмер, второе подключение отклоняется |
| `Shared` | конкурирующие консьюмеры, по кругу |
| `Failover` | один активный консьюмер и горячий резерв |
| `KeyShared` | конкурирующие консьюмеры с упорядочиванием по ключу |

Подписка начинается с проверки дескриптора: пустое имя подписки, пустой список топиков,
неправильное имя топика и шаблон, который не разбирается как регулярное выражение, возвращают
ошибку без обращения к брокеру.

Дескриптор пишется прямо в атрибуте `#[subscriber(..)]`, и то же объявление монтируется на
внутрипроцессном брокере (см. [Тестирование](#testing)). Файлу с маршрутами хватает одного импорта:
`ruststream_pulsar::prelude::*` вносит прелюдию фреймворка вместе с дескрипторами этого крейта, его
политикой публикации и настройками на сообщение.

```rust
--8<-- "crates/ruststream-pulsar/examples/pulsar_service.rs:handler"
```

Смонтируйте его на брокере:

```rust
--8<-- "crates/ruststream-pulsar/examples/pulsar_service.rs:app"
```

Топик можно назвать и строкой: `#[subscriber("orders")]` открывает на этом топике подписку `Shared`
с именем `ruststream`.

### Подписки по шаблону {#pattern-subscriptions}

`PulsarSubscription::pattern` читает в пространстве имён поиска каждый топик с именем, подходящим
под регулярное выражение, включая топики, созданные уже после подключения консьюмера. Список
топиков из `::topics([..])` - альтернатива с фиксированным составом: она охватывает ровно те
топики, которые вы назвали.

```rust
--8<-- "crates/ruststream-pulsar/examples/pulsar_pattern.rs:pattern"
```

Топики, попавшие под шаблон, пишут разные продюсеры, поэтому их полезные нагрузки не описываются
одной схемой. Пример берёт их байтами: newtype над `&'a [u8]` с `#[derive(Deserialized)]` называет
полезную нагрузку, не декодируя её, поэтому между брокером и обработчиком не работает ни один кодек.

### Пакеты {#batches}

Обработчик, который принимает срез, получает пакет целиком и завершает все его доставки разом:

```rust
--8<-- "crates/ruststream-pulsar/examples/pulsar_batches.rs:handler"
```

Точка монтирования называет одно число - размер пакета:

```rust
--8<-- "crates/ruststream-pulsar/examples/pulsar_batches.rs:app"
```

Клиент Pulsar отдаёт по одной доставке за раз, поэтому пакет собирает буфер самого фреймворка, на
стороне клиента. Пакет - это ровно то, что доставил подписчик, а не часть этого, и сообщений в нём
никогда не больше размера, названного при регистрации.

Пакет закрывается, когда в нём набралось названное число доставок или когда с первой из них прошло
`batch_wait`, - смотря что наступит раньше. Простаивающая подписка ждёт первую доставку сколько
угодно долго.
Увеличивая `batch_wait`, вы меняете задержку на более полные пакеты.

Пакетная подписка перематывается как любая другая: она открывается с выбранной позиции клаузой
`start_at(..)`, а тело пакетного обработчика перемещает её через `PulsarBatchContext` (см.
[Перемотку из обработчика](#repositioning-from-a-handler)).

### Отправка в dead-letter {#dead-lettering}

`DeadLetter::new("orders-dlq").max_deliveries(5)` отправляет сообщение в `orders-dlq` после пяти его
повторных доставок. Отрицательное подтверждение увеличивает счётчик доставок. `ack_timeout`
увеличивает его и без nack: повторно доставляет всё, что осталось неподтверждённым дольше таймаута.
И то и другое - настройки консьюмера Pulsar, а не машинерия этого крейта.

## Подтверждение {#acknowledgement}

| Исход обработчика | Операция Pulsar |
| --- | --- |
| `HandlerOutcome::ack()` | подтвердить сообщение |
| `HandlerOutcome::retry()` | отрицательное подтверждение с запросом повторной доставки |
| `HandlerOutcome::drop()` | подтвердить сообщение |

`drop` подтверждает, потому что завершающего отказа в Pulsar нет. Poison-сообщения уводит политика
dead-letter, до которой доходят повторные доставки.

Клиент ставит подтверждения в очередь, поэтому завершение доставки, вернувшее `Ok`, означает, что
подтверждение поставлено в очередь на консьюмере, а не что брокер его подтвердил. Закончившаяся
подписка закрывает свой консьюмер.

### Отложенные повторы {#deferred-retries}

Отрицательное подтверждение Pulsar не задаёт задержки, поэтому исход
`HandlerOutcome::retry_after(delay)` идёт отложенным путём самого фреймворка: сообщение публикуется
заново, когда задержка истекла, а подписка сообщает, куда. Топик сам себе адрес, поэтому подписка на
один топик отвечает этим топиком, и в области, которой задали `retry_via(publisher)`, настраивать
больше нечего. Годятся оба написания одного топика: дескриптор
`PulsarSubscription::new(topic, subscription)` и голое `#[subscriber("orders")]`.

Список топиков и шаблон не отвечают ничем. Любой из них мог бы назвать топик, который читает
подписка, но копия пришла бы не в тот топик, с которого сообщение снялось, и обработчик,
ветвящийся по топику доставки, выбрал бы не ту ветку. Приложение, где `retry_via` задан над такой
подпиской, отказывается стартовать, и ошибка называет подписку. Дайте каждому топику свою подписку
или оставьте область без издателя повторов - там `retry_after` вырождается в немедленную повторную
доставку.

## Перемотка {#seeking}

`PulsarPosition` называет место в хранимом журнале топика. Это позиция, с которой клауза
`start_at(..)` открывает подписку, и позиция, к которой перематывается обработчик:

| Позиция | Что означает |
| --- | --- |
| `PulsarPosition::earliest()` | начало журнала: заново доставляется каждое хранимое сообщение |
| `PulsarPosition::latest()` | конец журнала: только сообщения, опубликованные после перемотки |
| `PulsarPosition::timestamp(millis)` | время публикации в миллисекундах с начала эпохи Unix |
| `PulsarPosition::MessageId(..)` | позиция доставленного сообщения, прочитанная по ключу `Position` |

Перемотка на позицию, снятую с доставки, заново доставляет ровно это сообщение, а за ним - остаток
журнала по порядку. Форма с временной меткой сохраняет собственную семантику времени публикации
Pulsar.

Клауза `start_at(..)` открывает подписку с выбранной позиции, как в примере с шаблоном выше. Сама
клауза - это перемотка, и она выполняется при каждом старте. Это не серверная начальная позиция
Pulsar, которая действует только при первом создании подписки. Подписка Pulsar - долговечное
состояние на стороне брокера, поэтому `start_at(PulsarPosition::earliest())` перематывает её
сохранённый курсор и проигрывает хранимую историю заново при каждом запуске сервиса. Без клаузы
подписка продолжает с этого курсора.

### Перемотка из обработчика {#repositioning-from-a-handler}

`PulsarContext` - контекст, который подписка Pulsar отдаёт своим обработчикам. В нём два ключа:
`Position` - место этого сообщения в журнале, и `SeekHandle` - ручка перемотки подписки. Обработчик
привязывает ключ параметром через экстрактор `Ctx` фреймворка или читает его через
`ctx.context(..)`, если уже объявил контекст. Точка монтирования не добавляет ничего.

```rust
--8<-- "crates/ruststream-pulsar/tests/seek_context.rs:delivery"
```

Тело пакетного обработчика называет вместо него `PulsarBatchContext`: ручку перемотки без позиции.
Пакет охватывает много доставок, поэтому цель перемотки берётся из самих элементов - пакет
`&[Message<H, T>]` читает её из контракта заголовков каждого элемента. Запрос `Position` в пакетном
теле не компилируется.

```rust
--8<-- "crates/ruststream-pulsar/tests/seek_context.rs:batch"
```

Пакеты собираются на клиенте (см. [Пакеты](#batches)), а ручка перемотки под ними - собственная
ручка подписки.

Одна перемотка охватывает все топики и все разделы консьюмера этой подписки. Доставки, уже стоявшие
в очереди в момент перемотки, отбрасываются, а не попадают в обработчик, поэтому поток продолжается
с целевой позиции. Единственное исключение - пакет, который ещё собирается: он закрывается с теми
доставками, которые уже успел взять.

## Публикация {#publishing}

`PulsarPublish` - политика, которая конструирует издателя `PulsarPublisher` и инстанцирует его при
старте на подключённом брокере. Это политика публикации этого брокера по умолчанию, поэтому
обработчик, смонтированный простым `include`, отвечает через неё. Тип ответа называет топик, в
который уходит ответ, через `#[outgoing(name = "receipts")]`. Тип ответа, который топик не называет,
уходит в тот, что назвала клауза `publish("receipts")`. Та же политика инстанцируется и на
внутрипроцессном брокере, поэтому точка монтирования называет `Publish` один раз и работает на
любом из двух (см. [Тестирование](#testing)).

Файл с маршрутами импортирует `ruststream_pulsar::prelude::*`, где политика лежит под своим
понятийным именем, без префикса: `.out(Reply, Publish)` читается одинаково, на каком бы брокере ни
работал сервис. Тело обработчика импортирует вместо этого `ruststream::prelude::*` и называет только
вещи фреймворка, ограничивая внедрённый слот той трейт-совместимостью брокера, которая ему нужна
(`Out<impl Publisher>`); единственное исключение - тело, которое задаёт ключ партиционирования (см.
[Настройки на сообщение](#per-message-settings)). Имя с префиксом, `PulsarPublish`, остаётся в корне
крейта для файла, который монтирует два брокера сразу.

Издатель держит по одному продюсеру на топик: продюсер создаётся при первой публикации в этот топик
и закрывается в `shutdown`. Каждая публикация дожидается квитанции брокера, поэтому успешная
публикация означает, что брокер сохранил сообщение. Издателя можно взять и у брокера до старта
приложения вызовом `PulsarBroker::publisher()`, и у подключённой формы вызовом
`ConnectedPulsarBroker::publisher()`.

### Настройки на сообщение {#per-message-settings}

Ключ партиционирования - то, чем одна публикация отличается от следующей. По нему маршрутизация по
ключу размещает сообщение, и по нему же упорядочивает подписка `KeyShared`. Шаг `partition_key`
называет его для отправляемого сообщения:

```rust
--8<-- "crates/ruststream-pulsar/tests/publish_options.rs:handler"
```

Шаг записывает одно поле `PulsarPublishOptions`, типа настроек этого крейта, и возвращает билдер
публикации. Поэтому сообщение уходит через тот слот, который задала точка монтирования, и в кодеке
этого слота, а тестовая обвязка показывает на этом слоте ключ, названный в месте вызова. Точка
монтирования для этого не объявляет ничего: всё объявление - `.out(Ledger, Publish)`, а публикация,
не назвавшая шага, уходит без ключа.

Тело, которое называет этот шаг, импортирует `ruststream_pulsar::prelude::*` и указывает тип
настроек на своём слоте, как в примере выше. Любое другое тело импортирует только
`ruststream::prelude::*`.

В заголовке `partition-key` хранится тот же ключ в написании, которое читает любой брокер, поэтому
тело, которое пишет заголовки само, задаёт ключ сообщения, не называя ни одного типа Pulsar. Если в
публикации есть и заголовок, и шаг, действует шаг.

## Полезная нагрузка и заголовки {#payloads-and-headers}

Свойства сообщения Pulsar хранят заголовки напрямую, по одному свойству на заголовок. Программа не
на Rust видит обычное сообщение Pulsar, без конверта собственного формата фреймворка.

Заголовок `partition-key` - исключение. При публикации он становится собственным ключом
партиционирования сообщения: по нему маршрутизация по ключу размещает сообщение, и по нему
упорядочивают подписки `KeyShared`. При доставке он возвращается этим же заголовком. Шаг
`partition_key` задаёт тот же ключ, не трогая заголовки (см.
[Настройки на сообщение](#per-message-settings)).

## Локальная разработка {#local-development}

В репозитории лежит compose-файл, который поднимает Pulsar standalone, и рецепты just вокруг него:

```bash
just brokers-up                  # Pulsar standalone на 127.0.0.1:6650 (админка на 8080)
cargo run --example pulsar_service -- run
cargo run --example pulsar_pattern -- run
cargo run --example pulsar_batches -- run
just brokers-down
```

Набор тестов на настоящем брокере работает только при заданной переменной `PULSAR_TEST_URL`, а
иначе пропускается:

```bash
just test-brokers                # поднять брокер, интеграционные тесты и conformance, погасить брокер
```

или, на уже запущенном брокере:

```bash
PULSAR_TEST_URL=pulsar://127.0.0.1:6650 cargo test --workspace --all-features -- --test-threads=1
```

CI прогоняет тот же набор: интеграционные тесты, проверку жизненного цикла (`new` -> `connect` ->
подписка -> публикация -> приём -> ack -> `shutdown`, где издатель, созданный до остановки, обязан
вернуть ошибку после неё) и наборы совместимостей на перемотку и на пакеты.

## Тестирование {#testing}

Фича `testing` даёт `PulsarTestBroker` - брокер внутри процесса, который воспроизводит основную
маршрутизацию крейта без сервера и без сети. Жизненный цикл у него тот же, что и у настоящего
брокера, а обвязка `TestApp` запускает на нём сервис, поэтому обработчик тестируется внутри
процесса. См.
[Юнит-тестирование сервиса через `TestApp`](https://powersemmi.github.io/ruststream/latest/guides/testing/#unit-testing-a-service-with-testapp).

`PulsarSubscription` - источник подписки и для него, и для настоящего брокера, поэтому тест
монтирует то объявление, которое поставляет сервис, а не переписанное на голый топик: дескриптор
ниже - тот самый, что и в разделе [Дескрипторы подписки](#subscription-descriptors), без изменений:

```rust
--8<-- "crates/ruststream-pulsar/tests/descriptor_sources.rs:descriptor"
```

Его адресация соблюдается целиком: один топик, список `topics([..])` и регулярное выражение
`pattern(..)`, которое сравнивается с каждым топиком публикации, поэтому топик, впервые появившийся
уже после открытия подписки, доходит до обработчика так же, как на сервере.

Публикующая половина переносится так же. `PulsarPublish` конструирует издателя и на
внутрипроцессном брокере, и это его политика по умолчанию, поэтому точка монтирования остаётся
боевой - `.out(Reply, Publish)` или вовсе ничего для умолчания брокера, - а ответ читается из
журнала публикаций:

```rust
--8<-- "crates/ruststream-pulsar/tests/descriptor_sources.rs:reply_mount"
```

Маршрутизация идёт по хранимому журналу, а не по трубе, - именно это и позволяет вообще
протестировать сервис, который сам себя перематывает. Внутрипроцессный брокер отдаёт те же
`PulsarContext` и `PulsarBatchContext` с теми же ключами `Position` и `SeekHandle`. Подписка
открывается клаузой `start_at(..)` по хранимому журналу, а перемотка отбрасывает то, что стояло в
очереди, и набирает заново с целевой позиции:

```rust
--8<-- "crates/ruststream-pulsar/tests/seek_context.rs:delivery"
```

Каждый набор тестов фреймворка, который оправдан совместимостями этого крейта, прогоняется и на
внутрипроцессном брокере, и на настоящем: набор маршрутизации, `harness::lifecycle`,
`capabilities::seeking` и `capabilities::batches`. Сервис тестируется на этом брокере, поэтому
мерой служит контракт, а не случайное поведение брокера, а серверные прогоны подтверждают, что
два брокера сходятся. Из-за `harness::lifecycle` издатель, переживший `shutdown`, сообщает здесь
`NotConnected`, а не принимает сообщение молча, - ровно как дескриптор, ссылающийся на закрытое
соединение. Для запроса с ответом и для транзакций прогона нет ни там, ни там: крейт не реализует ни
одну из этих совместимостей по причинам из [таблицы совместимостей](#capabilities), поэтому ни один
из наборов не применим ни к одному из брокеров. Пакеты внутрипроцессный брокер собирает ровно так
же, как настоящий подписчик, - тем же буфером на стороне клиента поверх очереди по одной доставке, -
поэтому пакетный обработчик под тестом идёт тем же путём по коду, что и в бою.

Тип подписки соблюдается, потому что именно про него сервис пишет тесты. Сообщение доходит до каждой
подписки на его топик, а внутри одной подписки тип выбирает консьюмера, который его возьмёт:
`Exclusive` держит подписку за одним консьюмером и отклоняет второе подключение, `Failover`
доставляет активному консьюмеру и повышает резервного, когда тот уходит, `Shared` раздаёт по кругу,
а `KeyShared` разделяет по ключу партиционирования. Поэтому два обработчика на одной общей подписке
делят прогон между собой здесь так же, как в бою, а `nack(requeue = true)` возвращается в подписку,
и повтор может достаться соседу.

Четыре вещи всё же не дотягивают до сервера, и тест, который на них опирается, опирается не на тот
брокер:

- `KeyShared` распределяет по остатку от деления хеша ключа на число консьюмеров, а не по
  диапазонам хешей Pulsar. Один ключ остаётся на одном консьюмере - это и есть свойство, которое
  стоит тестировать, - но какой именно это консьюмер, здесь и на сервере разное, как и то, что
  перетасует приход или уход консьюмера.
- Перемотка двигает того консьюмера, который её попросил; на сервере курсор принадлежит подписке,
  поэтому перемотка от одного консьюмера общей подписки двигает и его соседей.
- Доставка, отклонённая больше `max_deliveries` раз, продолжает возвращаться, а не уходит в топик
  dead-letter: для `dead_letter` нужен серверный счётчик доставок на сообщение, которого этот
  транспорт не ведёт.
- `ack_timeout`, кредит и тайминги повторной доставки здесь ни на что не влияют: это часы сервера, а
  не транспорта.

Последние две вещи - продуктовое поведение, которое набор тестов проверяет на настоящем брокере;
первые две - места, где эта модель грубее серверной.

Имена топиков маршрутизируются буквально: пространства имён, относительно которого их разрешать,
здесь нет. `orders` и `persistent://public/default/orders` здесь два адреса, а на сервере один
топик. Шаблон сравнивается с тем же буквальным именем, а сервер сравнивает его с полным, поэтому
неякорный `orders-.*` отбирает одни и те же топики в обоих случаях, а шаблон с якорем `^` над голым
именем подходит здесь и больше нигде.

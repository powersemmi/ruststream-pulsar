# Повторное чтение и перемотка

Это руководство заново читает хранимый журнал топика Pulsar: с начала при каждом запуске или с позиции, на которую перематывает обработчик.

Подписка - это курсор в журнале топика, и хранит его сервер.
Перемотка переставляет этот курсор, и подписка продолжает чтение с нового места.

Пример - сервис поиска.
Он хранит балансы счетов, построенные по реестру проводок, и поисковый индекс заказов.
`Search` заменяет клиент поискового кластера.

## Позиции {/* #positions */}

[`PulsarPosition`](../components/positions/index.md) называет место в журнале топика:

| Позиция | Где |
|---|---|
| `PulsarPosition::earliest()` | самое старое хранимое сообщение |
| `PulsarPosition::latest()` | конец журнала: только сообщения, опубликованные после перемотки |
| `PulsarPosition::timestamp(millis)` | первое сообщение, опубликованное в этот момент или позже, в миллисекундах от начала эпохи Unix |
| `PulsarPosition::MessageId(..)` | доставленное сообщение, его позицию даёт [`Position`](../components/context/index.md) |

[`start_at`](../components/positions/start-at.md) перематывает подписку при каждом запуске сервиса.
`balances` при каждом запуске читает реестр с самой старой хранимой проводки, поэтому балансы строятся заново.
Без `start_at` существующая подписка продолжает с того места, где остановились её консьюмеры, а новая начинается с конца топика.

У Pulsar есть собственная начальная позиция, но она действует только при создании подписки.
`start_at` действует и на уже существующую подписку.
Каждый запускаемый экземпляр переставляет общий курсор, поэтому экземпляры сервиса с `start_at` перечитывают журнал при запуске любого из них.

[`SeekHandle`](../components/positions/seek.md) - ручка перемотки самой подписки, и `index` получает её из [контекста Pulsar](../components/context/index.md).
Когда поисковый кластер теряет индекс, `index` перематывает подписку на самый старый хранимый заказ, и каждый заказ индексируется заново.
В ручной форме обработчик называет своим контекстом `PulsarContext` и получает ручку перемотки через `ctx.context(SeekHandle)`.

Перемотка переставляет всю подписку: каждый её консьюмер, каждый топик, который она читает, и каждую партицию.
Доставки, которые уже стоят в очереди подписки, отбрасываются, и журнал читается с нового места.

Часто нужны ещё две перемотки:

- `PulsarPosition::timestamp(millis)` пропускает участок плохих данных: подписка продолжает с первого сообщения, опубликованного после него.
- Позиция доставки, полученная через `Ctx<Position>`, доставляет ровно это сообщение снова, а за ним остаток журнала по порядку.

[Пакетный обработчик](../components/context/batch-context.md) перематывает так же, через `PulsarBatchContext`. В нём есть ручка перемотки и нет позиции, потому что пакет охватывает много сообщений.

## Что доступно для повторного чтения {/* #what-a-replay-reaches */}

Повторное чтение читает то, что топик ещё хранит.
По умолчанию Pulsar удаляет сообщение, когда его подтвердили все подписки.
[Политика хранения](https://pulsar.apache.org/docs/next/cookbooks-retention-expiry/) в пространстве имён сохраняет подтверждённые сообщения до заданного объёма или в течение заданного времени:

```bash
docker compose exec pulsar bin/pulsar-admin namespaces set-retention public/default \
  --size 1G --time 3d
```

Нехранимый топик ничего не хранит, поэтому перемотка в нём ничего не перечитывает.

## Проверка перемотки {/* #testing-a-seek */}

Тесты в файле примера запускают приложение внутри процесса.
Pulsar внутри процесса хранит журнал каждого топика, поэтому перемотка там перечитывает его, как на сервере.
Тест публикует три заказа одной серией через `broker.publisher()`, поэтому все три ждут в подписке, прежде чем обработается первый.
Затем `tb.settle()` ждёт, пока у подписки не кончится работа.
Очередь, которую оставил прошлый запуск сервиса, существует только на сервере, поэтому `start_at` над такой очередью проверяют живые тесты крейта.
